# Qt6 + libmpv 播放器第三版 UI 阶段设计任务书

> 版本定位：第三版 Airy Glass 独立 UI/UX 设计任务书  
> 设计基准：已确认的浅雾、柔紫蓝、柔焦、半透明玻璃、强留白、轻悬浮视觉方向  
> 设计对象：Qt6 + libmpv 桌面播放器  
> 文档性质：设计执行基线，不替代源码开发 R2–R14 任务书  
> 组织原则：按窗口、控制系统、Inspector、状态、Preferences、设计系统、原型与交付组织，不把播放器功能误写成网页“页面”  
> 设计阶段编号：D0–D9

## 统一执行策略

本任务书学习现有 `docs/plans` 与 `docs/plans/stages` 的写法：阶段目标明确、职责边界明确、Atomic Task 可独立验收、先搭正确骨架再逐步收口；但**内容完全独立于旧 R2–R14 开发任务书**。

整个第三版 UI 设计按以下节奏推进：

1. **视觉母语优先**：先锁定已经确认的 Airy Glass 基准，不再在执行中回到深色黑蓝播放器、传统后台面板或旧 IINA 复刻。
2. **产品结构优先**：先明确 Player Window、Video Viewport、Floating Header、OSC、Inspector、Overlay、Preferences、Mini/Fullscreen 的空间关系，再设计局部控件。
3. **真实场景优先**：所有组件都必须来自真实播放器场景；不为了“组件库看起来完整”提前创建没有产品落点的组件。
4. **源组件优先**：一旦发现跨场景重复的视觉或交互，必须回到 Token / Primitive / Component / Surface 源处理，不在多个成品画面分别打补丁。
5. **全局回刷**：圆角、玻璃材质、间距、图标、时间轴、按钮尺寸、显隐逻辑发生基准变化时，必须全局同步，不允许只改一个窗口模式。
6. **最后文档化**：Handoff、变量统计、组件清单、交互说明必须从最终设计反推，不允许先写过期规格再强迫产品稿适配。

### 默认硬阻断

出现以下任一情况时，不得继续铺开后续设计：

- 主播放器框架仍与前两版视觉骨架高度相似；
- 同一控件在主窗口、Fullscreen、Mini 中出现三套独立实现；
- Playlist / Tracks / Subtitles / Chapters 形成四套不同的侧板语言；
- 窗口、OSC、Inspector、Preferences 之间明显不像同一个产品；
- 关键控件存在肉眼可见的未对齐、非光学居中、行高漂移、间距不一致；
- Figma 组件源和成品实例出现无法解释的硬编码颜色、圆角、阴影、尺寸分叉；
- 状态展示依赖“大色块、大圆按钮、大红框”掩盖层级问题；
- 为了追求玻璃效果牺牲可读性、焦点可见性或复杂视频背景下的辨识度。

## 模块化总原则

- Figma 的 Page 只是设计文件分类容器，不代表产品“页面”。
- 产品结构必须按 **Window / Region / Overlay / Inspector / State / Component** 理解。
- 主播放器窗口只拥有布局组合，不拥有各 Feature 的内部组件实现。
- OSC 只负责播放器控制系统，不承载 Playlist/Tracks/Settings 的业务内容。
- Inspector Shell 只负责容器、标题区、尺寸、材质、开合和切换；Playlist/Tracks/Subtitles/Chapters 各自只负责内容模块。
- HUD / Toast / Dialog / Error Overlay 是不同反馈层级，禁止混成一个万能浮层。
- Mini Player / Fullscreen 是同一播放器的不同窗口模式，不复制第二套播放状态。
- Token 是视觉真值；Component 是交互/几何真值；成品画面只消费它们。
- 任何一个 Figma Component 一旦需要承担第二项可独立演进职责，应升级为 Component Set 或拆成子组件，不继续在单组件内部堆 Variant 例外。

# Stage D0：视觉基准与设计治理

## 1. 本阶段最终要得到什么

把第三版从“我喜欢这张参考图”变成一套可执行的视觉约束。D0 完成后，后续任何设计者都能判断一个新控件、新浮层、新窗口是否仍属于第三版，而不是凭个人感觉继续发散。

## 2. 本阶段怎么快速推进

不制作完整组件库。先冻结五件事：**产品空间结构、视觉关键词、禁用旧视觉、设计文件组织、评审方式**。当前已确认的三张核心框架作为产品视觉基准，不回退到旧项目结构。

## 3. 目标设计结构

```text
Player Product
├─ Player Window
│  ├─ Video Viewport
│  ├─ Floating Header
│  ├─ OSC
│  ├─ Inspector Host
│  └─ Transient Overlay Host
├─ Window Modes
│  ├─ Windowed
│  ├─ Fullscreen
│  └─ Mini
├─ Preferences Window
└─ Design System
   ├─ Foundations
   ├─ Primitives
   ├─ Components
   └─ Surfaces
```

Figma 文件建议只作为分类：

```text
00 Direction
01 Foundations
02 Components
03 Player Window
04 Inspector
05 States & Feedback
06 Preferences
07 Window Modes
08 Prototype
09 Handoff
```

## 4. 阶段主链

```text
Confirmed Visual References
  ↓
Visual Principles / Product Structure
  ↓
Framework Screens
  ↓
Design System Extraction
  ↓
Feature Expansion
```

## 5. 关键状态 / 资源归属

- 视觉方向：D0 基准文档。
- 产品空间关系：Player Window System。
- 颜色/材质/间距数值：D1 Token。
- 控件几何和交互：D3/D8 Component。
- Figma Page：只做分类，不承担产品语义。

## 6. Atomic Tasks
### D0-01 冻结第三版视觉母语

**目的**  
把已确认的浅雾、柔焦、柔紫蓝、软玻璃、强留白、漂浮控件正式定义成唯一视觉方向。

**主要模块 / 设计对象**  
`00 Direction` / Visual Principle board

**主要链路**  
`reference → visual principles → product decisions`

**实施重点**  
明确 airy / ethereal / soft glass / pastel glow / luxury minimal / sharp grotesk / editorial spacing 的产品化含义；每个词必须能对应到实际布局、材质或交互。

**基本验证**  
用 Main Player / Fullscreen / Inspector 三张框架逐条核对；任何一张若依赖黑色实体面板或大面积高饱和蓝块则失败。

**完成判断**  
三张框架在不同构图下仍然能被识别为同一视觉系统。
### D0-02 冻结旧视觉禁用清单

**目的**  
防止执行中再次滑回第一/第二版的深色播放器骨架。

**主要模块 / 设计对象**  
Direction / Do & Don't

**主要链路**  
`old visual patterns → explicit rejection rules`

**实施重点**  
列出禁止的大蓝圆播放键、厚底栏、纯黑 Drawer、后台卡片墙、重描边、硬阴影、卡片套卡片、以蓝色填满 selected 等模式。

**基本验证**  
任取前两版截图与第三版框架做视觉差异检查。

**完成判断**  
后续评审可以明确指出“违反哪条禁用规则”，而不是只说‘不好看’。
### D0-03 定义播放器产品结构而非页面结构

**目的**  
确保后续 Playlist/Tracks/Subtitles/Chapters 不被误当成四个独立页面。

**主要模块 / 设计对象**  
Player Window / Inspector / Overlay / Preferences / Window Modes

**主要链路**  
`window → regions → feature hosts → content states`

**实施重点**  
明确 Fullscreen/Mini 是 Window Mode；Playlist/Tracks/Subtitles/Chapters 是同一 Inspector Shell 的内容状态；Loading/Error 是 Overlay State。

**基本验证**  
用结构树检查是否存在重复 Shell、重复 OSC、重复 Inspector。

**完成判断**  
所有设计对象都有唯一结构归属。
### D0-04 建立视觉评审基线

**目的**  
把对齐、留白、光学中心、复杂背景可读性纳入每阶段固定检查。

**主要模块 / 设计对象**  
Review checklist / screenshot matrix

**主要链路**  
`design change → representative screenshots → visual QA`

**实施重点**  
固定至少 5 类检查：几何对齐、光学居中、间距节奏、材质可读性、跨窗口一致性。

**基本验证**  
Main / Fullscreen / Inspector 各输出 100% 截图进行人工复检。

**完成判断**  
每个阶段都能用同一 QA 维度关闭，不靠主观印象。

## 7. 框架打通后优先修复

- 任何仍像旧深色播放器的结构。
- 浅色只是“换皮”而骨架没变。
- Main / Fullscreen / Inspector 三张之间圆角、玻璃、字体密度不统一。
- Figma 分类名称被误当成产品页面概念。

## 8. 本阶段最小可评审里程碑

在一个 Direction board 中，能同时看到视觉关键词、Do/Don't、产品结构树以及三张已确认框架缩略图；设计者能够在不查看旧项目的前提下继续设计。

## 9. 阶段关闭条件

第三版视觉方向、产品结构、禁用旧视觉和评审规则全部冻结。没有“之后再决定主色/Drawer/OSC 结构”的关键歧义。

## 10. 本阶段暂不要求

不要求把所有 Token 精确到最终值；不要求建立全组件库；不要求写开发实现细节。

## 11. 后续扩展位置

任何新视觉想法先判断是否改变 D0 基准；若改变，应视为设计方向变更，而不是在单个 Feature 内偷偷处理。
