# Qt6 + libmpv 播放器第三版 UI 阶段设计任务书

> 版本定位：第三版 Airy Glass 独立 UI/UX 设计任务书  
> 设计基准：已确认的浅雾、柔紫蓝、柔焦、半透明玻璃、强留白、轻悬浮视觉方向  
> 设计对象：Qt6 + libmpv 桌面播放器  
> 文档性质：设计执行基线，不替代源码开发 R2–R14 任务书  
> 组织原则：按窗口、控制系统、Inspector、状态、Preferences、设计系统、原型与交付组织，不把播放器功能误写成网页“页面”  
> 设计阶段编号：D0–D9

## 统一执行策略

本任务书学习现有 `docs/plans` 与 `docs/plans/stages` 的写法：阶段目标明确、职责边界明确、Atomic Task 可独立验收、先搭正确骨架再逐步收口；但**内容完全独立于旧 R2–R14 开发任务书**。

整个第三版 UI 设计按以下节奏推进：

1. **视觉母语优先**：先锁定已经确认的 Airy Glass 基准，不再在执行中回到深色黑蓝播放器、传统后台面板或旧 IINA 复刻。
2. **产品结构优先**：先明确 Player Window、Video Viewport、Floating Header、OSC、Inspector、Overlay、Preferences、Mini/Fullscreen 的空间关系，再设计局部控件。
3. **真实场景优先**：所有组件都必须来自真实播放器场景；不为了“组件库看起来完整”提前创建没有产品落点的组件。
4. **源组件优先**：一旦发现跨场景重复的视觉或交互，必须回到 Token / Primitive / Component / Surface 源处理，不在多个成品画面分别打补丁。
5. **全局回刷**：圆角、玻璃材质、间距、图标、时间轴、按钮尺寸、显隐逻辑发生基准变化时，必须全局同步，不允许只改一个窗口模式。
6. **最后文档化**：Handoff、变量统计、组件清单、交互说明必须从最终设计反推，不允许先写过期规格再强迫产品稿适配。

### 默认硬阻断

出现以下任一情况时，不得继续铺开后续设计：

- 主播放器框架仍与前两版视觉骨架高度相似；
- 同一控件在主窗口、Fullscreen、Mini 中出现三套独立实现；
- Playlist / Tracks / Subtitles / Chapters 形成四套不同的侧板语言；
- 窗口、OSC、Inspector、Preferences 之间明显不像同一个产品；
- 关键控件存在肉眼可见的未对齐、非光学居中、行高漂移、间距不一致；
- Figma 组件源和成品实例出现无法解释的硬编码颜色、圆角、阴影、尺寸分叉；
- 状态展示依赖“大色块、大圆按钮、大红框”掩盖层级问题；
- 为了追求玻璃效果牺牲可读性、焦点可见性或复杂视频背景下的辨识度。

## 模块化总原则

- Figma 的 Page 只是设计文件分类容器，不代表产品“页面”。
- 产品结构必须按 **Window / Region / Overlay / Inspector / State / Component** 理解。
- 主播放器窗口只拥有布局组合，不拥有各 Feature 的内部组件实现。
- OSC 只负责播放器控制系统，不承载 Playlist/Tracks/Settings 的业务内容。
- Inspector Shell 只负责容器、标题区、尺寸、材质、开合和切换；Playlist/Tracks/Subtitles/Chapters 各自只负责内容模块。
- HUD / Toast / Dialog / Error Overlay 是不同反馈层级，禁止混成一个万能浮层。
- Mini Player / Fullscreen 是同一播放器的不同窗口模式，不复制第二套播放状态。
- Token 是视觉真值；Component 是交互/几何真值；成品画面只消费它们。
- 任何一个 Figma Component 一旦需要承担第二项可独立演进职责，应升级为 Component Set 或拆成子组件，不继续在单组件内部堆 Variant 例外。

# Stage D5：播放状态与反馈系统

## 1. 本阶段最终要得到什么

让播放器在 Empty、Loading、Playing、Paused、Buffering、Seeking、Ended、Error 等状态下都有准确且克制的视觉反馈，并明确 HUD、Toast、Inline、Overlay、Dialog 的优先级。

## 2. 本阶段怎么快速推进

先建立 Feedback Priority 和 Overlay Host，再设计各状态。不要为每个状态画一张完全不同的播放器；同一窗口几何保持不变，只改变真正需要变化的状态层。

## 3. 目标模块结构

```text
Feedback System
├─ Player Status Overlay
│  ├─ Empty
│  ├─ Loading
│  ├─ Buffering
│  ├─ Paused
│  ├─ Ended
│  └─ Error
├─ Seek Preview
├─ HUD
├─ Toast
├─ Inline Feedback
└─ Dialog
```

## 4. 阶段主链

```text
Playback / Action Result
  ↓
Feedback Priority
  ↓
Overlay / HUD / Toast / Dialog
  ↓
Timeout / Dismiss / Recovery
```

## 5. 关键状态 / 资源归属

- Playback state：产品播放状态投影。
- HUD：短时、高频、可合并反馈。
- Toast：短时、非阻断结果。
- Overlay：当前媒体状态。
- Dialog：需要用户决策。
- Error 不允许同时在 Overlay + Toast + Dialog 重复轰炸。

## 6. Atomic Tasks
### D5-01 Feedback Priority Matrix

**目的**  
定义各种状态和错误应落在哪一层。

**主要模块 / 设计对象**  
Feedback matrix

**主要链路**  
`state/error → severity/recoverability → surface`

**实施重点**  
先定规则再画视觉；例如不可播放媒体→Error Overlay，设置保存失败→Toast，需要恢复播放选择→Dialog。

**基本验证**  
用 20 个典型事件做归类演练。

**完成判断**  
同一事件只有一个主反馈入口。
### D5-02 Empty / Loading

**目的**  
设计空媒体和加载状态。

**主要模块 / 设计对象**  
Status Overlay

**主要链路**  
`no media/loading → overlay`

**实施重点**  
空态允许明确打开媒体入口；Loading 轻量、不用大 Spinner 卡片。

**基本验证**  
首次启动/加载网络/纯音频。

**完成判断**  
状态清楚但不抢占整个画面。
### D5-03 Playing / Paused

**目的**  
定义播放中与暂停时 UI 的差异。

**主要模块 / 设计对象**  
Player visual state

**主要链路**  
`transport state → header/osc/hud`

**实施重点**  
Playing 默认最少 UI；Paused 可提高 OSC 可见性，但不需要中央巨大暂停图标。

**基本验证**  
播放/暂停快速切换。

**完成判断**  
暂停状态自然可感知。
### D5-04 Buffering / Seeking

**目的**  
设计缓冲和拖动/等待 Seek 的反馈。

**主要模块 / 设计对象**  
Buffering/Seek overlay

**主要链路**  
`buffer/scrub/pending → feedback`

**实施重点**  
Buffering 不覆盖用户 Pause 意图；Seeking preview 与 buffering 语义分开。

**基本验证**  
buffer 10/50/unknown、scrub/pending。

**完成判断**  
用户能判断‘网络缓冲’和‘我正在拖动’。
### D5-05 Ended

**目的**  
设计播放结束后的最小恢复/下一步入口。

**主要模块 / 设计对象**  
Ended overlay

**主要链路**  
`EOF → ended → replay/next`

**实施重点**  
保持视频最后一帧或背景；动作数量少。

**基本验证**  
单项/有下一项/repeat。

**完成判断**  
结束态不伪装成错误态。
### D5-06 Error Overlay

**目的**  
设计不可播放、加载失败、渲染错误等媒体级错误。

**主要模块 / 设计对象**  
Error overlay

**主要链路**  
`failure → message/action → recovery`

**实施重点**  
不使用整圈红框；错误层级通过 icon/title/detail/action 表达。

**基本验证**  
可恢复/不可恢复/未知错误。

**完成判断**  
用户知道发生什么以及能做什么。
### D5-07 HUD / Toast / Dialog

**目的**  
建立三类反馈的正式组件与消息密度。

**主要模块 / 设计对象**  
Feedback components

**主要链路**  
`action result → component → timeout/dismiss`

**实施重点**  
Volume/Seek/Speed HUD 要支持合并；Toast 不刷屏；Dialog 仅用于决策。

**基本验证**  
连续音量、连续 Seek、错误、恢复播放。

**完成判断**  
高频操作不会造成视觉噪音。

## 7. 框架打通后优先修复

- 状态卡片过大、颜色过重。
- Buffering/Error/Loading 同时显示。
- HUD 连续消息刷屏。
- Dialog 在玻璃背景上对比不足。
- 暂停状态被设计成另一个完整页面。

## 8. 本阶段最小可评审里程碑

同一 Player Window 中可演示 8 个核心状态，以及 Volume/Seek HUD、Toast、Resume/Error Dialog。

## 9. 阶段关闭条件

状态优先级明确；视觉克制；恢复动作完整；复杂背景可读。

## 10. 本阶段暂不要求

不定义后端错误码细节；只定义产品级展示契约。

## 11. 后续扩展位置

截图成功、轨道切换等新反馈优先复用 HUD/Toast，不新建第五种反馈层。
