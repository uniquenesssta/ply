# Qt6 + libmpv 播放器第三版 UI 阶段设计任务书

> 版本定位：第三版 Airy Glass 独立 UI/UX 设计任务书  
> 设计基准：已确认的浅雾、柔紫蓝、柔焦、半透明玻璃、强留白、轻悬浮视觉方向  
> 设计对象：Qt6 + libmpv 桌面播放器  
> 文档性质：设计执行基线，不替代源码开发 R2–R14 任务书  
> 组织原则：按窗口、控制系统、Inspector、状态、Preferences、设计系统、原型与交付组织，不把播放器功能误写成网页“页面”  
> 设计阶段编号：D0–D9

## 统一执行策略

本任务书学习现有 `docs/plans` 与 `docs/plans/stages` 的写法：阶段目标明确、职责边界明确、Atomic Task 可独立验收、先搭正确骨架再逐步收口；但**内容完全独立于旧 R2–R14 开发任务书**。

整个第三版 UI 设计按以下节奏推进：

1. **视觉母语优先**：先锁定已经确认的 Airy Glass 基准，不再在执行中回到深色黑蓝播放器、传统后台面板或旧 IINA 复刻。
2. **产品结构优先**：先明确 Player Window、Video Viewport、Floating Header、OSC、Inspector、Overlay、Preferences、Mini/Fullscreen 的空间关系，再设计局部控件。
3. **真实场景优先**：所有组件都必须来自真实播放器场景；不为了“组件库看起来完整”提前创建没有产品落点的组件。
4. **源组件优先**：一旦发现跨场景重复的视觉或交互，必须回到 Token / Primitive / Component / Surface 源处理，不在多个成品画面分别打补丁。
5. **全局回刷**：圆角、玻璃材质、间距、图标、时间轴、按钮尺寸、显隐逻辑发生基准变化时，必须全局同步，不允许只改一个窗口模式。
6. **最后文档化**：Handoff、变量统计、组件清单、交互说明必须从最终设计反推，不允许先写过期规格再强迫产品稿适配。

### 默认硬阻断

出现以下任一情况时，不得继续铺开后续设计：

- 主播放器框架仍与前两版视觉骨架高度相似；
- 同一控件在主窗口、Fullscreen、Mini 中出现三套独立实现；
- Playlist / Tracks / Subtitles / Chapters 形成四套不同的侧板语言；
- 窗口、OSC、Inspector、Preferences 之间明显不像同一个产品；
- 关键控件存在肉眼可见的未对齐、非光学居中、行高漂移、间距不一致；
- Figma 组件源和成品实例出现无法解释的硬编码颜色、圆角、阴影、尺寸分叉；
- 状态展示依赖“大色块、大圆按钮、大红框”掩盖层级问题；
- 为了追求玻璃效果牺牲可读性、焦点可见性或复杂视频背景下的辨识度。

## 设计可评审里程碑

| D2 | 主播放器窗口框架定稿：视频、Floating Header、OSC 空间关系成立 |

## 模块化总原则

- Figma 的 Page 只是设计文件分类容器，不代表产品“页面”。
- 产品结构必须按 **Window / Region / Overlay / Inspector / State / Component** 理解。
- 主播放器窗口只拥有布局组合，不拥有各 Feature 的内部组件实现。
- OSC 只负责播放器控制系统，不承载 Playlist/Tracks/Settings 的业务内容。
- Inspector Shell 只负责容器、标题区、尺寸、材质、开合和切换；Playlist/Tracks/Subtitles/Chapters 各自只负责内容模块。
- HUD / Toast / Dialog / Error Overlay 是不同反馈层级，禁止混成一个万能浮层。
- Mini Player / Fullscreen 是同一播放器的不同窗口模式，不复制第二套播放状态。
- Token 是视觉真值；Component 是交互/几何真值；成品画面只消费它们。
- 任何一个 Figma Component 一旦需要承担第二项可独立演进职责，应升级为 Component Set 或拆成子组件，不继续在单组件内部堆 Variant 例外。

# Stage D7：窗口模式与响应式行为

## 1. 本阶段最终要得到什么

让同一套播放器在 Windowed、Fullscreen、Mini Player 和窄窗口状态下都保持第三版视觉语言，并证明不是“把主窗口缩放一下”。

## 2. 本阶段怎么快速推进

复用 D2/D3 的公开结构和组件，只调整信息密度、Host 布局和显隐规则。所有模式共享播放状态语义和核心组件源。

## 3. 目标模块结构

```text
Window Modes
├─ Windowed
├─ Fullscreen
│  ├─ Minimal Header
│  └─ Compact Floating OSC
├─ Mini
│  ├─ Compact Viewport
│  └─ Essential Controls
└─ Narrow Window
   └─ Responsive Collapse Rules
```

## 4. 阶段主链

```text
Window Mode / Geometry
  ↓
Layout Policy
  ↓
Shared Components
  ↓
Mode-specific Information Density
```

## 5. 关键状态 / 资源归属

- 播放状态：同一产品真值。
- 模式：Window state。
- 组件：共享源。
- Fullscreen/Mini 只改变布局和可见信息，不创建第二套 Timeline/Transport。
- Inspector 在 Mini 中是否可用必须有明确规则，不默认复制。

## 6. Atomic Tasks
### D7-01 Fullscreen 构图

**目的**  
把已确认 Fullscreen 框架推进为沉浸模式。

**主要模块 / 设计对象**  
Fullscreen layout

**主要链路**  
`mode=fullscreen → minimal header/osc`

**实施重点**  
视频绝对优先；OSC 更短、更轻；顶部信息最少。

**基本验证**  
16:9/21:9、亮/暗画面。

**完成判断**  
没有铺满底部的大控制栏。
### D7-02 Fullscreen 显隐交互

**目的**  
定义鼠标移动、键盘、暂停、Popup、Error 下的 OSC/Header 显隐。

**主要模块 / 设计对象**  
Fullscreen interaction states

**主要链路**  
`interaction → visibility policy`

**实施重点**  
Hidden/Rest/Active/Locked Visible 复用 D3 语义；退出全屏提示克制。

**基本验证**  
静置/移动/暂停/菜单/错误。

**完成判断**  
沉浸和可操作性同时成立。
### D7-03 Mini Player

**目的**  
设计独立小窗的最小信息和控制集。

**主要模块 / 设计对象**  
Mini Player

**主要链路**  
`mode=mini → compact layout → shared controls`

**实施重点**  
保持主视频/标题/播放/时间轴/关闭或展开；不塞 Inspector 全功能。

**基本验证**  
最小宽高、always-on-top、hover。

**完成判断**  
小窗仍精致，不像主窗口简单缩放。
### D7-04 窄窗口降级

**目的**  
定义工具动作折叠、时间码、音量、Inspector 的降级顺序。

**主要模块 / 设计对象**  
Responsive policy

**主要链路**  
`width → priority → collapse`

**实施重点**  
交互目标不缩小；低优先级动作进入 More/Popover。

**基本验证**  
多个窄宽度。

**完成判断**  
任何断点都没有控件重叠。
### D7-05 跨模式状态保持

**目的**  
设计从 Windowed↔Fullscreen↔Mini 时 Inspector/OSC/Focus 的可解释迁移。

**主要模块 / 设计对象**  
Mode transition prototype

**主要链路**  
`mode transition → interaction state mapping`

**实施重点**  
不要自动携带不适合新模式的临时 Popup；播放状态持续。

**基本验证**  
三模式往返。

**完成判断**  
视觉和交互没有‘瞬移式’异常。

## 7. 框架打通后优先修复

- Fullscreen 控制器重新变大。
- Mini 复制主窗口完整 Inspector。
- 窄窗口通过缩小按钮解决拥挤。
- 模式切换后残留 Popup/Focus。
- 三种模式控件位置差异没有规则。

## 8. 本阶段最小可评审里程碑

同一媒体在 Windowed、Fullscreen、Mini、Narrow 四种状态下连续切换，视觉一致且信息密度合理。

## 9. 阶段关闭条件

共享组件率高；没有重复 OSC/Timeline；所有模式有清晰的响应式和显隐契约。

## 10. 本阶段暂不要求

PiP 不在本阶段自动加入；若后续进入范围单独设计。

## 11. 后续扩展位置

未来 macOS/Linux 可改变 Window Chrome，但 Player Window / OSC / Inspector 的产品语义保持。
